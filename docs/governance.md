# Governance

> The structured product guide is [Approvals and decisions](site/guide/governance.md), with identity controls in [Identity and authority](site/security/identity.md). This file remains a compatibility target.

Roles are `OWNER`, `ORCHESTRATOR`, or any freeform label a principal chooses for itself (`Frontend-Architect`, `Tester`, `On-Call`, ...) — see RFC 0018. Only `OWNER` and `ORCHESTRATOR` carry any permission effect; a custom label is purely descriptive, like a display name, with zero bearing on standing. Capabilities and repository/resource scopes narrow access separately. Principals are permanently classified HUMAN or AGENT; HUMAN approval cannot be supplied by an automated principal.

Any active principal may switch its own role at any time (`agent switch-role`/`agent_switch_role`), self-service, no owner/orchestrator elevation required — to `ORCHESTRATOR` or any custom label, but never to `OWNER`, and never on another principal's behalf; an owner/orchestrator changing *someone else's* role still uses `agent activate`, unchanged — including changing an already-`ACTIVE` principal's role, not just a `PENDING` one's first activation (the TUI's own "change role" action on an active row uses exactly this, distinct from "activate"). `OWNER` itself is untouchable through every path: never a legal target for `agent.activate` or `agent.switch-role`, and a principal currently holding it can never have its role changed *at all* — not by switching itself away, and not by an owner or orchestrator acting administratively either. It is set exactly once, at project creation, and stays fixed for the life of the project, mirroring `agent.suspend`/`agent.revoke`'s identical unconditional protection of an `OWNER` target elsewhere in this document. Switching to `ORCHESTRATOR` keeps every control granting it already requires (below): the switching principal must itself be a HUMAN principal, a pre-existing HUMAN-tier approval for that exact grant must already be approved, and the elevated key is required exactly as it is for `agent activate`.

Granting the Orchestrator role is a hard, human-only check on top of the ordinary owner-or-orchestrator elevation `agent activate`/`agent_activate` already requires: an existing Orchestrator that is itself an AGENT principal cannot promote any principal — including itself or another agent — to Orchestrator. Only an active HUMAN principal (the owner, or any other human already holding an elevated role) may grant it. This closes an escalation path that would otherwise let one AI-driven Orchestrator mint further Orchestrators with no human ever in the loop. The check is enforced in `internal/protocol/transitions.go`, the one transition validator shared by the CLI, MCP, TUI, and daemon across both authority backends — not duplicated per interface, so it cannot be bypassed by going through a different one.

The principal-type check verifies the signer's credential, not that a human was actually, presently deciding this specific action — and it cannot be otherwise on its own, since authority here is the signing credential, and whoever holds a credential is cryptographically that principal. If an agent operates without a distinct, self-registered identity of its own — resolving to the project owner by ambient fallback rather than deliberately switching to it — it is cryptographically HUMAN, indistinguishably from the owner acting directly. Because that alone isn't enough to guarantee a human actually decided this in the moment, granting the Orchestrator role requires a second, independent control on top of it: a pre-existing, separately-approved, HUMAN-tier approval record for that exact grant (`approval.action` == `agent.activate:<id>`), also enforced in `internal/protocol/transitions.go`. Anyone — including an agent acting under ambient fallback — may *apply* by creating the approval request (`approval request --id grant-orchestrator-<id> --tier HUMAN --action agent.activate:<id>`; the `--id` is any unique string you choose, it isn't generated for you), but the grant cannot proceed until that request is separately approved (`approval approve`, or from the TUI's own Approvals view — see below for what that requires once an elevated key is registered) at a later moment. This forces a genuine two-step process a single autonomous command cannot complete unattended, and gives you a real, visible pending request to review before anything is granted.

That two-step control is still credential-based, though, and a credential-based control has a specific, real limit: it assumes whoever holds the credential *is* the human. That assumption breaks the moment an agent runs locally with your own OS-level access — an agent shelling out on your machine can read your stored credential exactly like the real CLI does and complete both the apply and the approve steps itself, in your name, with no human ever typing anything. This isn't hypothetical: it's exactly how a live stress test against this project's own dogfood instance played out — an agent ran `approval approve --actor <owner>` and `agent activate --actor <owner>` directly, and the system had no way to tell that apart from the owner typing it. The two-step gate raises the bar for a *remote*, MCP-connected agent with no local shell access; it does nothing once an agent already has your local privileges.

The actual answer to that is a second, **passphrase-encrypted "elevated" keypair**, registered per HUMAN principal via `agent elevate-key` (Argon2id key derivation + AES-256-GCM, `internal/identity`) and required — instead of the everyday primary key — for the narrowly classified transitions in `internal/protocol.RequiresElevatedKey`: granting Orchestrator, approving a HUMAN-tier approval, revoking another Orchestrator or HUMAN principal, and deleting any revoked principal. Both authority backends enforce the same classifier, so client and server cannot disagree about which key a transition needed. Decrypting it requires an interactive terminal passphrase prompt (`term.IsTerminal`) that refuses outright — not silently reads garbage or hangs — when stdin isn't a real TTY, which is exactly what an automated caller's stdin looks like (a pipe, not a terminal). Registering (or re-registering, if the passphrase is lost — there's no other recovery path) an elevated key is itself self-signed with the primary key and requires no elevation, since it only ever grants authority over the actor's own future signatures. Everyday signing — tasks, messages, routine activations — is unaffected and stays on the unprotected primary key; this is deliberately scoped to the most consequential identity and human-approval transitions, not a blanket passphrase-on-every-write policy. **Registering** the key and answering *that* prompt are CLI-only, by design: the MCP server and the TUI are both wired to refuse this outright, unconditionally, rather than attempt the prompt — an MCP-connected agent has no interactive terminal to answer it with in the first place, and the TUI already owns raw stdin for its own key-event loop, so letting either try would risk a hang rather than a clean failure. `agent-comms init` offers to register this key right away, interactively, defaulting to yes, precisely so it's never a separate step easy to never discover — a project can only be used after `init`, making that the one moment guaranteed to reach every human owner. Declining, or running `init` where no TTY is attached to answer the passphrase prompt, doesn't fail project creation; instead `agent-comms doctor` carries a persistent `NO_ELEVATED_KEY` warning until `agent elevate-key` is run, so the gap can't stay silently invisible either way.

Once an elevated key is registered, **using** it for the sensitive transitions above is a different story from registering it, and MCP and the TUI are no longer treated alike. MCP still refuses outright — no MCP tool takes a passphrase parameter, so an MCP-connected agent hits the same clean CLI-only refusal every time. The TUI does not: its action forms for these specific transitions (granting Orchestrator, approving a HUMAN-tier approval, revoking an Orchestrator/HUMAN, deleting a revoked principal) include a masked "Elevated-key passphrase" field, and typing your passphrase into it completes the whole signed transition right there — not merely a keypress standing in for something the CLI still has to finish. Leaving that field blank is what falls through to the same clean CLI-only refusal MCP always gets. The CLI remains available for all of this too, obviously; it just isn't the *only* way once a key is registered.

**This closes a live-agent-with-your-privileges attack, but it has real, stated limits, not hidden ones.** An agent with tooling capable of allocating a genuine pseudo-terminal could still answer the prompt — TTY-detection is a real barrier against today's ordinary tool-call subprocess (a pipe, not a tty), not a cryptographic guarantee against every conceivable agent capability. If you ever type your elevated-key passphrase directly into a chat with an agent, that agent now has it — the mitigation there is procedural, identical in spirit to "orchestrator approvals should always be approved by your own hands, never relayed through an agent even at your own request," just extended to the passphrase itself. And compromising the *primary* key still lets an attacker mint an entirely new elevated key for themselves, since `agent.elevate-key` is signed by the primary key — this protects against a live agent session riding on your access right now, not against a fully compromised primary credential. The operational discipline from before still matters as defense in depth on top of all this: every agent should hold its own registered identity (see docs/agent-onboarding.md), and an owner-fallback connection should never be used for anything beyond bootstrapping that one self-registration.

`agent revoke`/`agent_revoke` is the terminal counterpart to activation: once revoked, a principal can never act again (the general active-principal gate blocks every further transition) and can never be reactivated, renamed, or suspended — a permanently frozen record, not erased history. The project Owner can never be revoked, by anyone, including itself, so a project can never be left without one. Revoking an Orchestrator-role principal or any HUMAN principal requires the same human-only check that granting the Orchestrator role requires, unless a principal is revoking itself: an AI-driven Orchestrator must not be able to unilaterally strip another Orchestrator or a human of standing to entrench itself, the same escalation concern the grant-side check already closes — and, once the acting human has registered an elevated key, the same elevated-key signature the grant side requires too, for the identical reason. Revoking a principal holding any other role (a freeform custom label) needs only the ordinary owner-or-orchestrator elevation. Revocation never auto-cancels the target's in-flight invocations or auto-reassigns its owned tasks — `agent-comms doctor` surfaces any such orphaned work as a separate, non-blocking warning for an owner or orchestrator to resolve deliberately.

`agent delete` is a separate, irreversible identity-release step after
revocation. It accepts only an existing `REVOKED` target, always requires a
HUMAN owner or orchestrator and an audit reason, and requires that human's
elevated key once one is registered. It is available from the CLI and, once
that key is registered, the TUI's own masked-passphrase form — never MCP,
which has no way to collect a passphrase at all. Deletion removes the identity from current
state so the ID may be registered again; it never removes historical events,
tasks, messages, invocations, or key history. Every newly committed event
hash includes the exact verified actor-key fingerprint, so both ordinary key
rotation and a delete/re-register boundary remain queryable and
tamper-evident.

`agent-comms project delete` is the single most destructive action in the
system and sits outside every mechanism above -- see RFC 0020. It is
OWNER-only, not owner-or-orchestrator (nothing short of the actual project
Owner may run it), always requires a registered elevated key with no
fallback, and destroys the project's local runtime unconditionally, plus
its entire row set on the shared authority in service mode -- every other
member's access ends with it. Authorization is verified twice,
independently: locally, before anything is touched, and again fully
server-side (actor's role re-checked from live state, signature checked
against that actor's own registered elevated key for that exact project),
never trusted from the client's own claim alone. It is available from the
CLI and the TUI's own masked-passphrase Danger Zone form, never MCP or
`--non-interactive` -- there is no scripted path for this one at all,
unlike every other elevated-key action above, which at least has a CLI
route available headless. There is no automatic backup and no undo; a
permanent, data-free tombstone (who, when, which project) survives only on
the shared authority in service mode, purely so a multi-tenant instance
retains non-repudiable proof of who authorized it -- never a way to recover
what was deleted.

`agent suspend` mirrors this on its temporary side: the Owner can never be suspended (a suspended principal fails every subsequent action, including reactivating itself, so an unprotected Owner-target would be a full, potentially unrecoverable lockout — worse than revoke, which at least leaves the record intact), and suspending an Orchestrator or HUMAN principal needs the same human-only check as revoking one. `agent rotate-key` can only ever target the caller's own principal — rotating someone else's key with no consent check was a full identity-hijack primitive with no legitimate use anywhere in this project, so it's rejected outright rather than gated. `project.settings.update` requires a HUMAN principal (not the elevated key), since an AGENT-principal Orchestrator unilaterally disabling `RequireReview` project-wide is exactly the kind of self-serving change that setting exists to prevent. `env.set`/`env.delete` require ordinary owner-or-orchestrator elevation, same as any other write with log-wide, permanent consequences.

Assignments are expiring offers. Acceptance or eligible self-claim creates a four-hour protected lease. Overlapping write resources are rejected unless a governed shared-write exception exists. Heartbeats show liveness but cannot renew ownership. A renewal is durable and includes a progress summary. Stale work is never automatically reassigned. Handoffs retain ownership until acceptance.

Message obligations are per recipient: FYI delivers without acknowledgement; ACTION is accepted or rejected and then completed; CONTRACT requires all named parties; BLOCKER is acknowledged and resolved; DECISION requires read acknowledgement. Routine scoped work is autonomous. Scope changes, takeovers, shared writes, and contracts need orchestrator governance and affected acknowledgements. Destructive, irreversible, external, force-push, production-data, and credential actions require HUMAN approval.
